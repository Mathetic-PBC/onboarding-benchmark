Stage 0: aggregating data

Every source is collected the same way. Each item in it, a file or a folder (a chat, an email thread, a document, a repo…), is copied as it is and gets one source_items row in the format below, through these steps. This is all code, with no model, and nothing goes into the library yet.

stepdone by
List every item in the sourceCode
Copy the original file or folder into the dataset, unchangedCode
Hash its content, so later changes can be spottedCode
Write its source_items row: source, title, dates, path to the copy, hash, and metadata (library_item_id left null)Code
Notes

Titles, dates and platform ids come straight from the export; missing values stay null. Listing an item never adds it to the library.

Wave 1: category list

Builds the list of projects to sort into. ChatGPT, Claude and a local agent (reading Claude Code, Codex and git history) each describe what the person worked on this past year. A merge step turns the three answers into one category list, and the person confirms it. No individual items are read.

stepdone by
Ask ChatGPT and Claude for a profile of the past yearModel (the assistant, from its memory)
Gather the Claude Code and Codex session folders and the git log of each repoCode
Read those logs and write the local profileModel (an agent with read-only file tools)
Merge the profiles, title, description and typed categories into the category listModel
Save the list as a generated_categories rowCode
Confirm or edit the listPerson
Notes

The three profile requests don't depend on each other, so they start together. If one is slow, the merge agent runs on what has arrived and runs again when the rest come in, so the first screen doesn't wait.

Claude Code keeps session transcripts only for a limited time, so its logs may cover weeks, not the year. Local git history fills in the earlier work. The time window is only a hint to ChatGPT and Claude; wave 2 enforces the real cutoff.

The merge agent keeps the person's typed categories as written, merges the same project under different names, adds Other / new topic, and records which profiles back each category. A category backed by only one source is flagged. The person confirms the draft with one edit, making 'Engelbart import quality' a sub-topic of Engelbart; everything after runs against catset_v2.

Wave 2: shallow pass

A quick first sort of every item. The agent sees only a short snippet of each (title, date, opening lines) and puts it in a category, or proposes a new one. Proposals that enough items back become new categories, and the items under Other are sorted again against them. Nothing is imported. The person then picks which categories to bring in.

stepdone by
List every source, build each item's snippet, cut the list into batches of about 50Code
Run the batches on 4 slots, retry failuresCode
Settle items from a free signal (folder, Drive folder, Gmail label)Code
Assign categories, confidence and evidence, flag items for a deeper read, propose new categoriesModel
Split each answer into one analyses row per item; drop evidence quotes not found in the itemCode
Group the proposed categories by name, with the items and sources behind eachCode
Merge proposals that name the same work, match them to categories already on the list, or drop them (wave2-new-categories-v1)Model
Keep new categories backed by 3+ items or items from 2+ sources, and save the list as catset_v3Code
Confirm the new categoriesPerson
Sort the items filed under Other, or that proposed a category, again against catset_v3Model (the shallow sort again)
Pick which categories go to the deep passPerson

run_001 skipped the new-categories step, so its proposals never became categories. From run_002 on it runs as new_categories then resort in run/pipeline.py; the deep pass then works from catset_v3.

How wave 2 runs

  • Listing: every source starts listing in code at the beginning, so nothing waits on the model. Sources read through the signed-in browser (ChatGPT, Claude, Drive, Gmail) may take turns; local sources don't.
  • Batches: each batch holds one source only, about 50 items, and goes to the shared wave2-shallow-sort skill in one call that returns one result per item. Code splits the answer into one analyses row per item. Batch size can vary by source: smaller for long chat digests, larger for metadata-only items like repos.
  • Free signals first: a session's folder, a Drive folder or a Gmail label can settle an item with no model call. It still gets an analyses row.
  • Slots: 4 slots run at once (a setting). Each slot takes one source and sorts it batch by batch; when it finishes, it takes the next source in line. Once no sources are left in line, free slots help with batches from sources still running.
  • Nothing is imported: wave 2 only adds analyses rows.

4 slots is a starting point; the benchmark compares 2, 4 and 8 for total time, rate-limit errors and accuracy.

Deep pass

A careful second look at the items in the picked categories. The agent reads each one in full and decides import, skip or unsure (pending). Code then adds the imported items to the library; this is the only step that writes to it.

stepdone by
Choose the qualifying items and assemble each one's full text (truncated past the budget)Code
Re-judge the item and decide import, skip or pendingModel
Validate the answer and write the analyses rowCode
Create or reuse the library row and write library_item_id backCode
Resolve pending itemsPerson

How the deep pass runs

  • Unsure items first: items wave 2 marked unsure or needs_deeper_read get their deep read before the person picks, so the counts they choose from are reliable. Anything still unclear is shown as its own 'unsure' group.
  • Full read: code gives the agent the whole item, or a large part of a long one. Folder items (an Overleaf project, a repo) are given file by file, with each unit naming its file.
  • Fresh judgment: the deep-pass skill re-judges from the full text without anchoring on the wave 2 result, quotes evidence, and gives a one-line reason when the assignment changes.
  • Decision: import (belongs to a picked category with high confidence), skip (belongs to none), or pending (still unclear; waits for the person and writes nothing).
  • Library write, by code: reuse a matching row (by library_item_id, origin_url or file) or create one through the existing import tool for that source, link it to its categories in library_categories, and write library_item_id back so a retry doesn't duplicate it.
  • Running: one item or a few per call, since inputs are large, on the same 4 slots as wave 2. It runs in the background, resumes after time limits, and later runs only handle new or changed items.
Notes

Compare analysis_001 with analysis_004. Both use catset_v2, so the rise from 0.55 to 0.93 came only from the deeper read. category_set_id is what lets you tell that apart from a change in categories.

Writing library_item_id back is what keeps a retry from creating a second library row.

The report is what the person sees at the end: found, looked at, brought in, skipped and unsure, per source. It says what each judgment was based on, so the limits are visible.

What each source becomes in the library

When the deep pass imports an item, today's import tools decide its library shape:

sourcelibrary entry today
ChatGPT, Claudeone Markdown file of the chat's turns, named by title (import_web_chats)
Claude Code, Codexone Markdown file of what you asked and what the assistant answered (import_chats)
Overleafthe unzipped project folder, the main .tex saved as a note, and up to three compiled PDFs
Google DriveDocs as Markdown with pictures, Sheets as a CSV table (first tab only), Slides as text, other files as they are
Gmailone note per thread, messages in order, attachment names only
Apple Notesone Markdown note per note, pictures saved
PDFsthe PDF as a file, tagged paper when it looks like one
GitHuba folder row tagged git
Granola, Linear, Notion, Evernotenotes the agent writes itself with add_note; no import-by-id tool yet

Open: some imports make several library rows for one item (Overleaf: a folder, a note and up to three PDFs). A single library_item_id can't record that; it needs to become a list, or point to one primary row with the others linked to it.

Rules the example relies on

  • Only the deep pass writes to the library. Stage 0, wave 1 and wave 2 only add analyses rows.
  • Reuse before insert. If library_item_id is already set, or a library row already matches the item's origin_url or file, the deep pass links that row ("op": "reuse") instead of inserting.
  • One library row per item, whatever its categories. An item in two categories gets one row and two library_categories links.
  • Unsure stays pending. A deep pass that ends below the confidence threshold sets "decision": "pending", writes nothing to the library, and the item appears in the "unsure" group.
  • ground_truth never reaches the agent. The benchmark compares it with the final decision and assignments afterward.
