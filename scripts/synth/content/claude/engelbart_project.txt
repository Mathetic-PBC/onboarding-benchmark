what should the rules be. be concrete
@assistant
Byte hashes only catch exact copies. For papers you need a ladder of keys, from strongest to weakest, and you should only *merge* on the strong ones.

**1. Exact copy** — `sha256(bytes)` equal → same file. Merge, keep both locations as provenance.

**2. Same work, identified** — DOI equal (normalized: lowercase, strip `https://doi.org/`), or arXiv id equal ignoring version (`2507.01842v1` ≡ `2507.01842`). → same work. Don't merge files; group them as **versions** of one paper.

**3. Same work, inferred** — no ids, but:
- normalized title similarity ≥ 0.92 (lowercase, strip punctuation and LaTeX, collapse whitespace; token-set ratio), **and**
- first author's last name equal, **and**
- year within ±1 (preprints are often a year earlier).
→ propose a version group, but mark it `confidence: inferred` so the UI can show "looks like the same paper".

**4. Everything else** — separate items.

Where the metadata comes from:
- Zotero: item fields (DOI, title, creators, date) are already there.
- Downloads PDFs: XMP metadata first, then the PDF info dict, then the first page text (largest font block on page 1 is usually the title). arXiv PDFs have the id stamped in the left margin, so regex `arXiv:(\d{4}\.\d{4,5})(v\d+)?` on page 1.

```ts
type Key = { kind: 'bytes' | 'doi' | 'arxiv' | 'title'; value: string };

export function dedupeKeys(item: ImportedItem): Key[] {
  const keys: Key[] = [{ kind: 'bytes', value: sha256(item.bytes) }];
  const m = item.meta;
  if (m.doi) keys.push({ kind: 'doi', value: normDoi(m.doi) });
  if (m.arxivId) keys.push({ kind: 'arxiv', value: m.arxivId.replace(/v\d+$/, '') });
  if (m.title && m.firstAuthorLast && m.year)
    keys.push({ kind: 'title', value: `${normTitle(m.title)}|${m.firstAuthorLast.toLowerCase()}` });
  return keys;
}
```

For Ostrowski: the camera-ready from Zotero has the DOI, the arXiv v1 has the arXiv id. Neither key matches the other directly, so it falls to rule 3 (title + first author + year 2025), which matches. That's the case where you want "versions", not a silent merge: the abstracts differ (0.69 vs 0.71 macro-F1), and a researcher may have annotated one and not the other.
@user
ok versions not merge, agreed. what about chats. claude export vs claude browser session will give the same conversation twice
@assistant
Chats are easier because they carry stable ids.

- **Same tool, same conversation id** → same item, regardless of how it arrived (export zip, browser session, re-import). Keep the newest `updated_at` version and record both arrival paths. A chat that grew since the last import should *update* the item, not create a second one.
- **Different tools** (a ChatGPT chat and a Claude chat about the same thing) → never dedupe. They're different conversations even when the content overlaps.
- **Branches**: ChatGPT conversations are trees. Import the current branch as the item, and keep other branches as hidden parts, not separate items.
- **Project chats**: the project is a container item; its chats are separate items with `parent_id = project`. Don't import a chat twice because it appears both in the chat list and the project's conversation list.

That last one is a real trap: the Claude projects endpoint lists the same chats you already got from the conversations list. Key on the conversation uuid and you're fine.
@user
slack file shares? someone shares a pdf in slack thats also in drive
@assistant
Treat the Slack message and the file as two things:

- The **message** is its own item (who shared it, when, what they said about it). Never dedupe it away; the "why" is often in the message.
- The **file** attached to it goes through the same paper/file ladder above. If its bytes match a Drive file, it's the same file with a second provenance edge ("shared in #research by Hudson, 2026-08-29").

So in the notebook the paper shows up once, with a trail: Zotero → Drive copy → shared in Slack. That trail is basically the product.

write this up as a short rules doc i can paste into the project knowledge. bullets, no prose
@assistant
**Import dedupe rules (draft, 2026-09-03)**

Files and papers
- Same bytes (sha256) → one file; keep every location as provenance.
- Same DOI, or same arXiv id ignoring version → one work; files become versions.
- Title similarity ≥ 0.92 + same first-author last name + year ±1 → proposed version group, `confidence: inferred`.
- Never merge versions into one file. Show "2 versions" on the paper.
- Metadata order for loose PDFs: XMP → info dict → page-1 text (largest block = title; arXiv margin stamp).

Chats
- Same tool + same conversation id → one item; newer `updated_at` wins; record each arrival path.
- Different tools → never dedupe.
- Branches → hidden parts of one item.
- Project chats → separate items with `parent_id`; don't double count from project listings.

Messages with files (Slack, Gmail)
- Message and attachment are separate items.
- Attachment goes through the file rules; a byte match adds provenance, not a new item.

Reporting
- After every import: count found / imported / merged / versioned / skipped per source.

fix it. and i want something that would have caught this
@assistant
The list call fetches one page and stops. Loop until a page comes back short:

```ts
const PAGE = 200;

async function listConversations(client: ClaudeClient): Promise<ConversationSummary[]> {
  const all: ConversationSummary[] = [];
  const seen = new Set<string>();
  for (let offset = 0; ; offset += PAGE) {
    const res = await client.get(`/chat_conversations?limit=${PAGE}&offset=${offset}`);
    const page = res.data as ConversationSummary[];
    for (const c of page) {
      if (!seen.has(c.uuid)) { seen.add(c.uuid); all.push(c); }
    }
    if (page.length < PAGE) break;
    if (offset > 50_000) throw new Error('claude list: runaway pagination');
  }
  return all;
}
```

The `seen` set matters: if a conversation gets updated during the import it can move between pages (the list is sorted by `updated_at`), and you'd otherwise get it twice or miss one. To be safe, after the loop do one more pass on the first page and add anything new.

**What would have caught it**

1. **A reconciliation line** in every import: `expected N (from source), fetched M, imported K, skipped S`. If the source gives a total, compare to it; if not, at least flag `fetched == PAGE` exactly as suspicious.
2. **A test with a fake client** returning 2.5 pages:

```ts
test('claude list paginates', async () => {
  const fake = fakeClient(Array.from({ length: 450 }, (_, i) => conv(`c${i}`)));
  const got = await listConversations(fake);
  expect(got).toHaveLength(450);
});
```

3. **Same audit for every connector.** If Claude had a hard-coded page, others might too. Grep for `limit=` across `connectors/`.

@assistant
Then start with measurement, because right now each problem was found by a pilot user noticing it. You want to find them before users do.

**1. Build a ground truth.** Take one real person's sources (yours is the obvious start) and produce a list of every item that *should* be imported, with:
- a stable item id and its source,
- which project(s) it belongs to (or none),
- known duplicate groups (same paper in Zotero + Downloads + a Slack share),
- hard cases: chats inside projects, a relevant passage buried in an unrelated chat, vague titles like "Untitled", a second email account.

**2. Define three metrics against it.**
- **Omission rate** = items in ground truth not imported / items in ground truth.
- **Duplicate rate** = extra copies of the same item or version group / items imported.
- **Wrong-item rate** = items imported and assigned to a project they don't belong to (or imported when they shouldn't be at all) / items imported.

**3. Then fix in order of what the numbers say**, re-running the benchmark after each change. Pagination was one omission cause; there will be others (archived chats, project-only chats, attachments).

**4. Design changes** to queue behind the measurement:
- Connect screen: flat grid + "Find your tool" search; drop "Other".
- Version groups for papers (the dedupe rules doc).
- Per-source reconciliation counts on the summary screen.
- Notion and Granola connectors.
@user
the ground truth is a lot of work. can i use synthetic data
@assistant
Partly. The trade-offs:

- **Real data** catches the failures you didn't think of (that's how pagination showed up). But it's private and you can't share it, and the labels take time.
- **Synthetic data** lets you plant exactly the hard cases you care about and label them for free, and you can cover tools you don't use (Notion, Granola, Perplexity). But you'll only find the failures you imagined.

A mix works: your real accounts as the base, plus synthetic items on platforms you barely use, each one labeled at generation time. Keep a column saying which is which so you can report metrics separately. If the importer does well on synthetic and badly on real, that's itself informative.
